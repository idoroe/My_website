## Project Overview

FinSight brings data engineering and machine learning together in a personal project built around 50,000 synthetic banking transactions. It covers the full path from generated data to a dashboard: transformation, quality checks, feature preparation, anomaly scoring, and an explanation a reviewer can read.

The core design question was how to make a flagged transaction useful to someone investigating it. That required a consistent data model and an interface that exposes the context behind unusual activity.

## Data Model and Transformations

A DuckDB star schema places `fact_transactions` at the center, with `dim_customer`, `dim_merchant`, and `dim_time` providing context. This separates transaction events from the customer, merchant, and time attributes used in analysis.

dbt organizes transformations into three layers:

- **Staging:** Clean the source records and cast fields to consistent types.
- **Intermediate:** Join related records and prepare derived features.
- **Marts:** Publish tables for analytics, model input, and the dashboard.

Data quality tests help make assumptions about the tables explicit. Keeping those transformations in dbt also makes it easier to trace where a model feature came from.

## Anomaly Scoring and Review

An Isolation Forest scores transaction features such as unusual amounts, timing, and activity patterns. FastAPI exposes the results to the React frontend.

The dashboard pairs flagged transactions with explanations ranked by severity. For example, a transaction may have an unusually large amount compared with the customer's baseline or occur at an uncommon time. These comparisons provide investigation context; they are not a determination that a transaction is fraudulent or a formal attribution of the model's decision.

The interface includes a transaction feed, summary statistics, and a detail view that keeps the score and supporting context together.

## Repeatable Setup

Docker Compose packages the API and frontend. A single-command startup runs synthetic data generation, dbt transformations, model training, and scoring on first boot. This makes the complete workflow available for local inspection without assembling each stage by hand.

## Engineering Takeaways

The most useful part of this project was connecting decisions across layers. A feature shown in the dashboard depends on a transformation, which depends on the meaning and quality of the source data. Clear boundaries make that chain easier to inspect and maintain.

The dataset is synthetic and the pipeline runs in batches. A useful next iteration would evaluate detection quality against known synthetic anomalies, check that historical features avoid future-data leakage, and measure how performance changes as the data grows. Streaming ingestion and model drift monitoring are further extensions.
