## Project Overview

PipelineX adds delivery checks and operational visibility to FinSight. It brings the application, monitoring configuration, and CI/CD workflow together so that building, checking, and investigating the stack follow a repeatable process.

It is a personal project using a production-style setup. The focus is on demonstrating the engineering decisions behind operating an application.

## CI/CD Workflow

The GitHub Actions pipeline has four stages:

1. **Lint:** Check Python code with Ruff.
2. **Test:** Run API tests with pytest.
3. **Build:** Create container images for the API and frontend.
4. **Scan:** Inspect built images with Trivy for high- and critical-severity vulnerabilities.

Required quality and security checks block merges when they fail. The scan occurs after the image build, so a failed scan rejects that image for subsequent delivery steps.

## Observability

Prometheus collects 15+ metrics, and provisioned Grafana dashboards surface request latency, error rates, and restarts. Keeping dashboard configuration with the project makes the monitoring setup repeatable.

The views support several different questions: Is traffic reaching the service? Are requests failing? Is latency changing? Can Prometheus still reach its target? Separating those signals is useful during diagnosis.

## Health Checks and Recovery

Docker Compose health checks cover four services. A health check reports whether a container is responding as expected. Docker restart policies handle process exits according to the configured policy; an unhealthy status alone does not restart a running container. [Docker documents restart behavior here](https://docs.docker.com/engine/containers/start-containers-automatically/).

That distinction shapes recovery testing. A process crash and an unresponsive process are different failure modes, and the recovery path needs to account for both. The project reduced manual restart time from minutes to seconds and supported incident diagnosis in under five minutes.

## Engineering Takeaways

Visibility is most useful when it answers a concrete question. Latency, request failures, target availability, and restart information provide different parts of the picture. A dashboard should help explain a failure and confirm recovery without relying on a single green status indicator.

Future extensions include centralized logs, alerting with documented response steps, and additional failure scenarios. Cloud provisioning and an orchestrated deployment would also make useful follow-on work.
